# R2.9 — Realistic CKKS Parameters, Security Assumptions, and Noise Validation

## Purpose

R2.9 establishes realistic CKKS parameter profiles and records the security and numerical assumptions used by `ccmm-rs`. It separates parameter-budget conformance, Gaussian-noise support, and full end-to-end security-bearing evaluation.

The current milestone validates realistic NTT/RNS CKKS arithmetic and Gaussian ciphertext encryption. It does **not** designate the research profiles as fully security-bearing because the current evaluation-key/relinearization construction is not yet noise viable with Gaussian evaluation-key error.

## Security methodology

The parameter profiles are selected against the published FHE security-guideline methodology used for the R2.9 analysis.

Relevant assumptions:

- classical security target: 128 bits;
- secret distribution: uniform ternary;
- error distribution: discrete Gaussian;
- Gaussian standard deviation: sigma = 3.19;
- reduction cost model: `RC.MATZOV`;
- Lattice Estimator methodology.

For the standard R2.9 profiles, `ccmm-rs` uses the published coefficient-modulus budgets under these assumptions. Direct Lattice Estimator tooling is retained for experimental, alternative, or future parameter sets; it is not presented as an independent re-estimation of every standard profile.

The implementation's ternary secret generator rejects the all-zero secret. This is the uniform-ternary model conditioned on a nonzero secret; the distinction is negligible at the realistic ring dimensions but remains explicit in provenance.

## Error-distribution implementation

R2.9 introduces an explicit RLWE error-distribution abstraction supporting bounded-uniform error for existing correctness/reference paths and discrete-Gaussian error for security-oriented experiments.

For RNS encryption, a single logical integer error polynomial is sampled and projected into every RNS limb. The limbs therefore represent the same logical error rather than independently sampled unrelated errors.

The discrete-Gaussian sampler is research infrastructure. It uses truncated support of +/-ceil(16 sigma), floating-point probability calculations, and a data-dependent sampling loop. It is **not** claimed to be a constant-time or hardened production sampler. Statistical sanity testing of empirical moments is implementation evidence, not a cryptographic security proof.

Existing zero-noise and bounded-noise APIs remain available as correctness/reference oracles.

## Realistic N=4096 CKKS validation

The realistic arithmetic path uses `research-4096`, N = 4096, 2048 canonical CKKS slots, initial scale = 2^35, NTT-backed RNS arithmetic, ciphertext-ciphertext multiplication, relinearization, one CKKS rescale, decryption, and canonical CKKS decoding.

The zero-noise realistic path validates arithmetic independently of noise behavior.

A separate end-to-end experiment validates Gaussian **ciphertext encryption** with sigma = 3.19 while retaining the zero-noise/reference multiplication key.

Observed result:

```text
GAUSSIAN_ENCRYPTION_PROFILE=research-4096
GAUSSIAN_ENCRYPTION_SIGMA=3.19
GAUSSIAN_ENCRYPTION_INPUT_SCALE=34359738368.000000
GAUSSIAN_ENCRYPTION_OUTPUT_SCALE=34360066050.125008
GAUSSIAN_ENCRYPTION_MAX_SLOT_ERROR=1.362844566946e-6
GAUSSIAN_ENCRYPTION_MAX_ERROR_SLOT=1536
```

Acceptance threshold:

```text
max slot error < 1e-3
```

Result: **PASS**.

This establishes that Gaussian ciphertext noise at the stated sigma is numerically compatible with the tested realistic N=4096 multiply/relinearize/rescale path when the evaluation key itself is generated without noise.

## Evaluation-key noise localization

A full experiment using Gaussian noise in both ciphertext encryption and multiplication-key generation produced unusably large numerical error. R2.9 therefore performed an A/B localization experiment.

### Case A — Gaussian ciphertexts, zero-noise multiplication key

```text
max slot error = 1.362844566946e-6
```

Result: **PASS**.

Evidence: `case-a-gaussian-ciphertext-zero-key.txt`.

### Case B — zero-noise ciphertexts, Gaussian multiplication key

```text
max slot error = 1.147366499223e5
```

Result: **FAIL**.

Evidence: `case-b-zero-ciphertext-gaussian-key.txt`.

The experiment localizes the observed numerical failure to the noisy evaluation-key/relinearization path rather than ordinary Gaussian RNS ciphertext encryption.

The current CRT-block evaluation-key construction uses CRT-idempotent-scaled targets. The observed behavior is consistent with evaluation-key noise amplification through this construction. R2.9 does not claim a more specific cryptographic root cause without a dedicated decomposition/noise analysis.

A future redesign may require a noise-controlled gadget decomposition, a special-modulus/hybrid key-switch construction with explicit P/Q accounting, or another quantitatively justified evaluation-key design.

## Security-bearing status

The research profiles intentionally retain:

```text
security_model = None
```

and therefore remain non-security-bearing in the public profile metadata.

Supported statements:

- realistic modulus budgets conform to the cited published 128-bit limits under the stated assumptions;
- the implementation supports a discrete-Gaussian research sampler with sigma = 3.19;
- logical Gaussian RNS ciphertext encryption has been validated end-to-end at N = 4096;
- the Gaussian evaluation-key path has been implemented and diagnostically exercised;
- the current evaluation-key/relinearization path is not noise viable under the tested Gaussian configuration.

The following statement is **not** made:

> The current `research-*` profiles constitute fully validated, production-ready, 128-bit-secure CKKS configurations.

Full security-bearing designation is deferred until the noisy evaluation-key path is redesigned and validated and all relevant auxiliary modulus material is included in security accounting.

## Auxiliary-basis accounting

Security accounting must distinguish the ordinary coefficient-modulus basis Q from any auxiliary/helper basis P used by hybrid or grafting paths.

Published Q-only bounds must not be applied to a path whose actual key-switch construction materially uses additional modulus P without accounting for the combined modulus required by the applicable security methodology.

Accordingly, R2.9's published-budget conformance statement applies to the ordinary research-profile Q chains. Hybrid/grafting auxiliary-basis security accounting remains outside the current security-bearing claim.
